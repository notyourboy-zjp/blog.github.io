1. LLM 和 Agent 有什么区别？

面试官常见问法

  • 你们项目里用的是 LLM 直接调用还是 Agent？为什么这么选？
  • Agent 比 LLM 多了什么？如果让你从零设计一个 Agent，你会怎么做？

LLM 本质

LLM（大语言模型）是条件概率模型，预测下一个token概率，是无状态函数：输入Prompt，输出文本，无记忆、无状态、对外部无知。

LLM 四大天花板

  1. 只会说不会做：能告知方法，无法自主执行
  2. 没有记忆：上下文窗口满则失忆，跨会话无留存
  3. 知识截止：训练数据有截止日期，无法获取最新信息
  4. 不会规划：无法自主拆解复杂任务

Agent 本质

Agent = LLM + 工具 + 记忆 + 规划，在循环中自主完成目标。

案例对比（查天气+取消跑步计划）

角色 实际行为
LLM 告知查询天气、取消计划的方法，不执行操作
Agent 调用天气API→查日历→删除计划→直接反馈结果

面试加分：Agent 四模块

  1. LLM（大脑）：理解意图、推理判断
  2. 规划模块：任务拆解、步骤排序
  3. 记忆模块：短期上下文+长期知识存储
  4. 工具模块：调用外部API、数据库等，是“手和脚”

2. Agent 和 Workflow 有什么区别？

核心区别

Workflow 控制权在代码，Agent 控制权在 LLM。

Workflow 详解

流程提前写死在代码，LLM 仅作为智能节点处理部分任务，步骤顺序、分支逻辑由开发者预定义。 示例：退款申请→LLM提取信息→查订单→LLM判断→执行退款/拒绝→发通知

Agent 详解

接收目标后自主规划执行路径，每一步由LLM决定，不写死代码，不同任务可走不同路径。

量化对比

维度 Workflow Agent
控制者 代码/开发者 LLM
Token消耗 低（约1x） 高（约4-8x）
可预测性 高 低
灵活性 低 高
适合任务 固定流程 开放式目标
调试难度 容易 困难
典型场景 订单处理/报表 研究分析/客服

生产实践：混合架构最优

Workflow 提供稳定骨架，Agent 处理异常与复杂情况，兼顾稳定与灵活。

3. Agent 有哪些工作模式？

模式一：ReAct（推理+行动）【默认首选】

核心循环：Thought（思考）→Action（行动）→Observation（观察）

  • 优点：透明可审计、灵活适应、通用性强
  • 缺点：Token消耗大、易死循环、延迟高

防死循环面试必背3方法

  1. 最大步数限制（通常15步）
  2. 重复动作检测（连续3次相同动作直接退出）
  3. 超时控制

class ReActAgent:
    def run(self, task, max_steps=15):
        steps = 0
        seen_actions = []
        while steps < max_steps:
            thought, action = self.llm_think(task, history)
            if steps >= max_steps:
                return "达到最大步数限制，任务终止"
            if action in seen_actions[-3:]:
                return self.llm_summarize("工具持续失败，给出答案")
            seen_actions.append(action)
            observation = self.execute(action)
            steps += 1

模式二：Plan-and-Execute（先规划再执行）

解决ReAct Token消耗高问题：先一次性生成完整计划，再按计划执行，可加入重新规划检查点适配偏差，Token消耗约为ReAct的20%。

模式三：Reflection（自我反思）

双Agent循环：生成Agent→审查Agent→迭代优化，适用于代码生成、法律文书、学术论文等高要求场景，可校正LLM幻觉。

模式四：Multi-Agent（多智能体协作）

协调Agent+专业Agent分工协作，主流框架：LangGraph、CrewAI、OpenAI SDK、AutoGen。 面试提醒：不要过早用多Agent，单Agent更稳定省钱，仅任务需并行/分工时引入。

4. Function Call 是什么？底层怎么实现？

核心认知

LLM不执行函数，仅输出结构化调用指令，由应用程序实际执行，保障系统安全。

四步工作流程

  1. 定义工具：向LLM声明可用函数、参数、描述
  2. LLM生成指令：输出结构化JSON而非普通文本
  3. 代码解析执行：解析指令并调用真实API
  4. 结果回传LLM：生成最终回答

Parallel Function Call（并行调用）

GPT-4o、Claude 3.5+支持一次多工具调用，延迟从T1+T2+T3降至max(T1,T2,T3)。

厂商格式对比

  OpenAI Anthropic Claude
工具定义 tools + function tools + input_schema
调用输出 tool_calls 数组 tool_use content block
结果传回 role: “tool” role: “user” + tool_result

5. MCP 是什么协议？解决什么问题？

核心问题：N×M集成爆炸

无MCP时，N个应用×M个工具需N×M套代码；MCP将其变为N+M，大幅降低维护成本。

MCP 架构三角色

  1. MCP Host：AI应用（Claude Desktop、自定义Agent）
  2. MCP Client：通信翻译官
  3. MCP Server：工具服务端，第三方服务实现

MCP 暴露三类资源

  • Tools：可执行操作（发消息、查数据）
  • Resources：可读数据源（文档、数据库）
  • Prompts：预设提示词模板

核心特性：工具动态发现

Agent启动时扫描Server，自动获取工具列表，新增工具无需重新部署代码。

安全设计

  1. 能力声明：仅调用声明工具
  2. 授权控制：敏感操作人工确认
  3. 审计追踪：全流程日志可查

底层协议

  • 本地：stdio
  • 远程：HTTP+SSE
  • 消息：JSON-RPC 2.0

6. Skills 是什么？和 Prompt 有什么区别？

核心作用

编码领域专家经验，让Agent知道特定场景该怎么做，而非仅调用工具。

Skills vs System Prompt

  System Prompt Skills
作用范围 全局生效 按需激活、场景触发
内容 通用行为规范 特定领域专业指导
激活方式 每次加载 匹配触发条件加载
可维护性 易臃肿 模块化、独立

Skill 文件标准结构

身份定位+工作流程+审查标准+输出规范+语气要求，教Agent方法论而非仅格式。

激活机制

用户输入→匹配关键词/语义→注入Skill上下文→按规范执行

7. Function Call、MCP、Skills 三者区别与协作？

通俗类比

  • Function Call：打电话的基础能力
  • MCP：公司统一通讯录+电话系统
  • Skills：岗位培训手册

技术三维对比

  Function Call MCP Skills
解决问题 LLM调用函数 工具集成标准化 领域知识编码
运行位置 应用程序 外部Server Agent上下文
技术本质 API协议 通信标准 提示词扩展
标准化 厂商不统一 开放统一 无统一标准

一句话总结

Skills 决定「怎么想」→ MCP 决定「用什么」→ Function Call 决定「怎么调」

8. A2A 协议是什么？和 MCP 的关系？

核心痛点

MCP解决Agent↔工具，未解决Agent↔Agent通信（跨框架、能力未知、任务无标准）。

A2A 核心概念

  1. Agent Card：智能体名片，声明能力、地址、认证
  2. Task：标准化任务生命周期（CREATED→PROCESSING→COMPLETED/FAILED）
  3. Message&Artifact：过程沟通+成果交付

MCP vs A2A

  • MCP：纵向，Agent↔工具连接
  • A2A：横向，Agent↔Agent协作 两者互补，非替代：Agent内部用MCP调工具，Agent间用A2A协作。

生态现状

  • MCP：事实标准，生态丰富
  • A2A：早期快速发展，Google主导

9. Agent 的记忆系统怎么设计？

两层记忆架构

  1. 上下文记忆（短期）：速度最快，容量有限，存当前对话、任务状态
  2. 外部记忆（长期）
    • 向量数据库：用户偏好、语义检索
    • 关系数据库：结构化事实、精确查询
    • KV存储（Redis）：任务状态、极速读写

记忆压缩策略（解决窗口溢出）

  1. 滑动窗口：丢弃最旧消息
  2. 摘要压缩：LLM总结旧对话
  3. 重要性过滤：仅保留关键信息

记忆读写时机

  • 写入：任务完成、用户信息更新、知识新增、失败复盘
  • 读取：任务开始、问题陌生、事实核查

10. Agent 的安全与可靠性如何保障？

四大安全威胁

  1. Prompt Injection：恶意指令注入
  2. 权限越界：超出操作范围
  3. 数据泄露：敏感信息外发
  4. 资源滥用：死循环耗成本

核心防御

  1. 最小权限原则：仅授予必要权限
  2. Human in the Loop：高风险操作人工审批（删数据、资金操作、改权限）

Prompt Injection 防御

  • 数据/指令分离
  • 输入过滤可疑内容
  • Prompt模板隔离
  • 上下文标记区分数据与指令

可靠性设计

  • 幂等性：重复执行结果一致
  • 回滚机制：重要操作备份可撤销
  • 超时+降级：失败有备用方案

11. RAG 和 Agent 是什么关系？

RAG 本质

检索增强生成，给LLM补充外部知识：检索文档→塞入Prompt→生成回答。

RAG vs Agent

  RAG Agent
目的 补充知识 完成任务
流程 固定（检索→生成） 动态（思考→行动）
工具 仅检索 任意工具
自主性 无 有

核心关系

RAG 是 Agent 的一个工具，Agent可按需调用RAG、API、代码执行器；进阶为Agentic RAG，让RAG自主判断检索策略。

12. 大厂真实面试追问汇总

系统设计类

  1. 设计企业级Agent系统：工具管理、记忆状态、可靠性、可观测性、安全
  2. 优化Token成本：精简工具、换执行模式、上下文压缩、模型路由、结果缓存

原理深挖类

  1. Function Call是Agent基石：解决LLM与外部世界交互的核心问题
  2. MCP协议：stdio/HTTP+SSE+JSON-RPC 2.0
  3. Skills vs Few-shot：Few-shot教格式，Skills教方法论

工程实践类

生产常见坑：死循环、幻觉工具、上下文污染、Token爆炸、Prompt Injection，对应解法需熟练掌握。

写在最后

Agent已从概念变为岗位刚需，面试官看重底层原理+协议关系+落地设计。吃透核心逻辑，即可应对技术栈迭代与面试深挖。
